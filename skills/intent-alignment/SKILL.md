# 意图对齐（Intent Alignment）

「Agent 按要求做了，但总不是用户想要的」——根因几乎都在 **意图 → 规格 → 实现** 之间丢信息，而不是实现本身写错。骂执行层没用，因为执行层照规格做得没错。要把反馈点往前挪、把意图做成工件、把每次纠正当成资产。

## 1. 先复述 + 列默认假设（反馈点前挪）

动手前，用自己的话复述任务，然后逐条列出你准备默认的假设：

- 「我默认用 X 方案，因为你没说」
- 「我默认目标是 Y，不做 Z」
- 「我默认继续在 A 硬件/版本上做，因为之前都在 A」

假设即分歧点。让人在几行字里纠正，而不是在成品里发现——计划阶段改是几分钟，成品阶段改是重做。

## 2. 歧义给选择题

遇到模糊点，不要默默选一个。给出 2-3 种理解让人挑。人是远好于作者的批评者：评价三个选项，比从头写需求便宜十倍。

## 3. 写负面边界（不做什么）

spec 优先写「不做什么」和边界情况，而不是只写「做什么」。沉默处即默认处——agent 过度交付（顺手重构、加没要的功能）的根源是边界没写清。

- 只做 X；觉得需要更多就先问，别做。
- 明确排除：不做重构、不加功能、不动无关模块。

## 4. 先写验收标准，人审再实现

先写测试 / 验收标准，让人审测试（审的是「可执行的 spec」），错配在零成本阶段被抓住，而不是实现后重做。

## 5. 让意图以工件形式存在（别只靠语言）

语言是意图的有损压缩，工件不是：

- 给例子 > 写描述：一个期望输出样例、一段参考代码、一个喜欢的 PR，携带的隐性信息远超一千字需求。
- 先做最薄的一版（IKIWISI）：很多用户看到才知道想要什么，让他骂原型，别让他骂成品。

## 6. 把每次「骂」转化为持久资产

结果不对时，别只发泄，做 mini retro：

1. 回头看你刚才的实现，哪个假设错了？
2. 把这条教训写进规则文件（AGENTS.md / CLAUDE.md / errata）。骂十次不如规则文件里多一行——本地先验逐步覆盖通用先验，下次会话直接生效。
3. 有条件再把教训沉淀成测试用例 / lint，让 agent 以后自查。

## 适用与边界

- 适用：任何「人给目标、agent 执行」的场景，尤其是长任务、多会话、跨硬件 / 跨版本、意图会漂移的项目。
- 关键前提：意图从没说出口时，agent 必须**主动问**（第 1-2 条），不能靠猜；人也要愿意把意图说出口。skill 治不了「从没说出口的意图」，只能治「说了但没对齐」和「对齐了但没记住」。
